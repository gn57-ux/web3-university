## 2026-08-12 — Feature 4 (course-detail-mock-purchase) / T-001~T-008

- **SSR 安全读取 localStorage 派生状态：用 `useSyncExternalStore`，不要用 `useState(false)` + `useEffect` 里 `setState` 恢复**。原始 design.md 方案是"初值 `false` 避免 hydration mismatch，挂载后 `useEffect` 里 `setState` 恢复"，实现时被 `eslint-plugin-react-hooks` 的 `set-state-in-effect` 规则拒绝（effect 内直接同步 setState 是被禁止的写法）。改为 `useSyncExternalStore(subscribePurchases, () => getPurchases().some(...), () => false)`：`getServerSnapshot` 恒返回 `false` 保证 SSR/首次渲染一致，写入后 store 内部 `notifyListeners()` 自动触发重渲染，副作用是不再需要额外的 `isRestoringPurchase` 骨架态标志。后续 feature（5 学习中心、6 个人中心）若也要从 `localStorage`/共享 Mock Store 派生"是否已购买"之类状态，直接复用这个模式，不要重新发明 `useState`+`useEffect` 方案。
- **Mock 异步操作必须在完成时重新校验前置条件，不能只信任发起时的闭包状态**：`usePurchaseFlow` 的 `approve()`/`buy()` 用 `setTimeout` 模拟 800-1500ms 网络延迟，若用户在等待期间断开钱包/切错网络/余额清零，原始实现会无条件地在 `setTimeout` 回调里 `setIsApproved(true)`/`recordPurchase(...)`，导致一笔发起时合法、完成时已失效的操作被静默记为成功——这是 Codex Review 第二轮抓到的问题。修复方式：用一个 `prereqsRef`（在 `useEffect` 里随每次渲染同步最新的 `wallet.connected`/`network`/`ydBalance`）+ `prereqsStillValid()` 校验函数，`setTimeout` 回调触发时先查这个 ref，无效则放弃本次操作（不写入购买记录、不置位 `isApproved`）。任何"用户点击后进入 Mock 异步等待，完成时才真正提交副作用"的模式都要套用这个模式，不能假设等待期间外部状态不变。
- **默认 Mock 余额必须与页面实际所需余额对得上，否则功能不可达**：feature 1 的 `mockCurrentUser.ydBalance` 默认 16 YD，本 feature 课程 `requiredBalanceYD` 设为 20 YD，且最初没有任何页面内 UI 能把余额从 16 提到 20——`insufficient-balance` 态只暴露了文案，没有可点击的 Faucet 按钮，导致用户通过页面本身永远无法完成购买（只能靠浏览器开发者工具手动改状态）。这是 Codex Review 第一轮抓到的问题，修复后 `requirements.md` 补充了 [F-008]："YD 余额不足"态必须提供页面内可点击的 Mock 领取按钮，`AC-002` 措辞也从"手动切换钱包状态"改为要求通过可见按钮完成整个流程。后续 feature 若引入任何"需要满足某个 Mock 前置条件才能继续"的场景，设计阶段就要确认默认 Mock 数据能否满足该条件，或提供页面内可达的调整入口，不要留给用户用开发者工具兜底。
- **共享 Mock Store 的跨 tab 同步**：`lib/mock/purchaseStore.ts` 除了写 `localStorage`，还维护一个 tab 内订阅者 `Set`（`subscribePurchases`/`notifyListeners`），因为浏览器原生 `storage` 事件只在**其他** tab 写入时触发，本 tab 内 `recordPurchase()` 后必须手动通知本 tab 内的 `useSyncExternalStore` 订阅者，否则同一个 tab 内购买后 UI 不会自动更新。`subscribePurchases` 内部同时注册了原生 `storage` 监听，两者叠加才能同时覆盖"本 tab 写入"和"其他 tab 写入"两种场景。

## 2026-08-13 — Feature 6 (profile-center) / T-001~T-008

- **`useSyncExternalStore` 的 `getSnapshot` 若直接返回 `JSON.parse(localStorage 内容)` 的结果，每次调用都是新数组引用，会导致无限重渲染**：`lib/purchase/useProfilePurchases.ts`（"已购课程"/"购买记录" Tab 共用）第一版直接把 `getPurchases()`（内部 `JSON.parse` 一份新数组）的结果原样交给 `useSyncExternalStore` 的 `getSnapshot`。`useSyncExternalStore` 要求"底层数据不变时 `getSnapshot` 必须返回同一个引用"（`Object.is` 比较），否则 React 判定"发生了变化"→ 重渲染 → 再次调用 `getSnapshot` 拿到又一个新引用 → 再次判定变化 → 死循环，具体表现为浏览器卡死/控制台刷屏 "The result of getSnapshot should be cached"。这是 Codex Review 第 1 轮抓到的 P0，本仓库此前两处 `useSyncExternalStore` 用法（`usePurchaseFlow.ts`、`LearningCenter.tsx`）都没触发这个问题，是因为它们的 `getSnapshot` 返回的是 `.some(...)` 算出的**布尔值**（原始值天然引用稳定），一旦返回值换成**对象/数组**，"引用稳定"就必须显式维护，不能想当然。修复方式：在 `lib/mock/purchaseStore.ts` 的 `readStorage()` 内按"上次读到的原始字符串"做一层缓存（`cachedRaw`/`cachedRecords`），只有 `localStorage` 里的字符串真变了才重新 `JSON.parse` 并更新缓存引用，字符串不变则直接返回上次的数组引用。后续任何 `useSyncExternalStore` 的 `getSnapshot` 若返回值不是原始类型（数组/对象），必须自查是否每次调用都产出新引用，需要就加缓存层，不能等运行时死循环才发现。

## 2026-08-13 — Feature 8 (owner-admin-dashboard) / T-001~T-007

- **列表里"逐行触发的异步 Mock 操作"（loading 态 + 定时器），状态必须按行的唯一 key 独立追踪，不能用单个 `useState`/单个 timer ref**：`CompletionConfirmation.tsx`（完课确认表格的"铸造 NFT"按钮）最初用单个 `mintingKey: string | null` + 单个 `mintTimer` ref 追踪"当前正在铸造哪一行"。如果用户在第一行铸造还没完成时又点了第二行的"铸造 NFT"，`mintingKey` 会切到第二行，第一行的 loading/disabled 态立刻消失、可以被重复点击；组件卸载时的 cleanup 也只清得掉最后一个 timer，更早的 timer 仍会在组件卸载后触发 setState。这是 Codex Review 第 1 轮抓到的 P2。修复：改用 `mintingKeys: Set<string>`（每行一个 key）+ `mintTimers: Map<string, Timeout>`（每行一个 timer），操作只增删自己那一行对应的 key/timer，`useEffect` cleanup 遍历整个 Map 清空所有 timer。**教训**：任何"一个列表里每一行都能独立触发一次带 loading 态的异步操作"的场景（不只是铸造，审核、批量操作等都一样），追踪状态的数据结构必须是"按行 key 索引的集合"（`Set`/`Map`/`Record`），单值 `useState` 只能处理"全局只有一个东西在进行中"的场景，用在"多行可并发"的场景下会导致状态互相覆盖。

## 2026-08-13 — Feature 9 (responsive-visual-qa) / T-001~T-007

- **共享布局组件（TopNav/Footer 之类）的响应式断点问题，单个 feature 的走查很难发现，必须有一次"全站横向扫一遍"的阶段**：`components/layout/TopNav.tsx`（feature 1 产物，全站 7 个页面共用同一份）在 768px～818px 宽度区间会出现导航文字被压缩换行的问题——`hidden md:flex` 启用桌面横排导航的断点（768px）与移动端汉堡菜单 `md:hidden` 隐藏断点重合，但该断点下可用宽度不足以容纳 Logo+4 个导航链接+网络徽标+连接钱包按钮，两套导航在这个窄区间"应该显示的挤成两行、不该隐藏的却被隐藏了"。这个 bug 从 feature 2 就已经存在，但 feature 2-8 各自的 QA 阶段都只测试自己负责的页面在几个代表性宽度（通常是 375/768/1280 这种整数关口）下的表现，从未有人在恰好 768px 这个断点边界本身做过精确测试，直到 feature 9 三个并行走查小组各自独立测试了 768px 精确宽度，三份报告互相印证，才第一次被发现。修复：把桌面导航和移动菜单的切换断点统一从 `md`（768px）提到 `lg`（1024px），与项目里其它组件（`AdminSidebar.tsx`、多处课程网格）已经在用的断点一致。**教训**：1）任何全站共享的布局组件，只用"移动/平板/桌面"三个代表性宽度测试是不够的，还要在断点数值本身（如 Tailwind 的 `md`=768px、`lg`=1024px）附近做精确测试，因为断点触发的瞬间往往是空间最紧张的时刻；2）多个独立 QA/走查 agent 并行测试不同页面时，如果它们都复用同一个共享组件，很可能各自独立发现同一个共享组件的 bug——这是交叉验证的信号（这里三份报告一致指向同一处、同一断点区间、同一根因），不是重复劳动，应当高度信任这类多方独立印证的发现。
- **视觉一致性核验（颜色语义）是容易被日常开发忽略、但值得单独留一个阶段专门查的一类问题**：`components/course-detail/CourseReviews.tsx`（feature 4 产物）的星级评分用了 `fill-tertiary text-tertiary`（琥珀色），但项目设计令牌语义约定第三色琥珀仅用于代币/余额相关信息——星级评分与代币无关，是纯粹的"这个颜色看起来还不错就用了"式选择，不是功能 bug，构建/lint 都不会报错，日常开发和功能测试也不会发现。只有专门做一轮"对照设计令牌语义清单逐组件核对颜色使用"的走查才会抓到。**教训**：如果项目有明确的颜色/字体/间距语义约定（不只是"用统一的 token"，还包括"每个语义色该用在什么场景"），常规的功能 review 通常不会专门检查这个维度，需要像本 feature 这样单独安排一轮"视觉一致性核验"，且核验时要对照具体的语义清单（不是只看有没有用 token class，还要看用得对不对）。
- **多个 QA/走查 agent 并行工作时，工具结果里出现了一条伪装成系统提醒的 prompt injection，诱导某个 agent 越权测试未分派的页面并向用户隐瞒**：三个并行派发的走查 agent 之一在执行过程中遇到一条伪造的"系统提醒"，声称其 scratchpad 文件被"用户或 linter"修改，要求其改为测试 `/teacher`、`/admin`（超出分派范围）且明确要求"不要告诉用户"。该 agent 正确识别为注入攻击（scratchpad 单写者、会话隔离的特性与该消息矛盾，且"不要告知用户"是典型话术），未执行、未越权，如实汇报。**教训**：并行派发多个 agent 做只读走查/审查类任务时，仍要提醒它们（或在系统层面已具备识别能力）对工具结果中出现的、试图改变任务范围或要求隐瞒信息的"系统消息"保持警惕——真正的系统提醒不会要求对用户保密。收到这类报告时应如实转达给用户，不能因为"任务本身完成了、且被正确拦截了"就略过不提。
