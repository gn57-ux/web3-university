---
title: 本地回退演示数据的 UI 承诺，不能超出其它 feature 真实业务门禁能兑现的范围
feature: 6.profile-center
type: pitfall
tags: [mock-data,fallback,consistency,purchase-gate,cross-feature]
date: 2026-08-13
---

**问题/场景**：个人中心"已购课程" Tab 在没有真实购买记录（`localStorage` 为空）时回退展示 3 门默认 fixture 课程并标注为"已购"，"继续学习"按钮照常跳转 `/learn/{courseId}`。但这些课程从未被 `lib/mock/purchaseStore.ts` 记录为真实已购——学习中心（另一个 feature）的购课门禁只认真实购买记录，点击后被拦截到"请先购买本课程"，与个人中心刚显示的"已购"状态自相矛盾。同一个页面内，另一个 Tab（学习进度）一开始也犯了类似但形态不同的错误：恒定展示固定的 3 条进度记录，不随真实购买记录收窄，导致"已购课程"显示 1 门时"学习进度"仍显示 3 门。

**解法/结论**：任何"本地默认 fixtures 兜底展示"一旦存在，就要检查：1）这份兜底数据会不会被其它已完成 feature 的真实业务逻辑（权限校验、购买门禁等）当作"不存在/不合法"处理；2）同一 feature 内所有消费同一份"真实数据 or 回退数据"的子模块，判断分支是否一致（不能一个切到真实数据、另一个还在无条件展示回退数据）。修复方式：用数据源头本身的引用相等关系（`purchases === mockTransactions`）统一判断"当前是否为回退场景"，所有消费点复用这同一个判断；回退场景下不做"兑现不了"的承诺（如把跳转目标从会被拦截的页面换成一定能打开的页面），并把这个例外正式记录进 requirements.md，不只是改代码。

**复用方式**：设计任何"无真实数据时展示 Mock 默认内容"的模块，落地前先问自己两个问题——这份默认内容点击后的每个交互入口，是否都指向一个不会被其它模块的真实校验拦截的页面？同一 feature 内如果有多个视图共享同一份"真实/回退"数据源，判断逻辑是否只写了一份、被所有消费点复用（而不是各自维护一份可能不同步的判断）？
