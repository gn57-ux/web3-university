feature: 9.responsive-visual-qa
type: pitfall
tags: [responsive,breakpoint,tailwind,shared-component,cross-feature,topnav]
date: 2026-08-13
---

**问题/场景**：全站共享的 `components/layout/TopNav.tsx`（挂载于根布局，7 个页面共用）用 `hidden md:flex` 启用桌面横排导航、`md:hidden` 隐藏移动端汉堡菜单，两者都在 Tailwind `md` 断点（768px）切换。但 768px 时可用宽度不足以容纳 Logo+4 个导航链接+网络徽标+连接钱包按钮，导致桌面导航的文字被压缩换行，而移动端汉堡菜单又已经被隐藏——用户在 768～818px 这个区间完全没有正常可用的导航。这个 bug 从最早引入 TopNav 的 feature 就已经存在，但后续每个 feature 的 QA 都只测试自己负责页面在几个代表性宽度（375/768/1280 这类整数关口，且往往是"用 768 这个数字代表平板"而不是真的测试"768 这个断点触发瞬间"）下的表现，直到专门的响应式 QA 阶段用多个独立 agent 分别测试不同页面、都精确测了 768px，才第一次发现——三份报告互相印证，指向同一根因。

**解法/结论**：把桌面/移动切换断点统一提高到项目里其它组件已经在用的断点（这里是 `lg`=1024px），消除"两套导航都不满足显示条件"的空档区间。

**复用方式**：1）测试任何用 Tailwind 断点做"移动/桌面"二选一切换的共享布局组件时，不能只测代表性宽度，还要精确测试断点数值本身（如 `md`=768px、`lg`=1024px），因为断点触发的瞬间往往是可用空间最紧张的时刻，最容易暴露"内容挤不下"的问题；2）多个独立 QA/走查任务并行测试不同页面、但都复用同一个共享组件时，如果它们各自独立发现了同一处共享组件的问题，这是强交叉验证信号，应当高度信任，不要当成重复劳动去重后只报一次就轻描淡写。
